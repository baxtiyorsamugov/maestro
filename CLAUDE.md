# CLAUDE.md — рабочая инструкция для агента

Этот файл читается автоматически в начале каждой сессии. Он описывает проект Maestro,
правила работы с кодом и жёсткие запреты. Держи его в актуальном состоянии: если меняется
архитектура или команда запуска — правь этот файл в том же коммите.

## 1. Что это за проект

**Maestro** — Telegram-бот для записи клиентов к мастерам (барберы, стилисты) в Ташкенте
плюс веб-панель администратора. Язык интерфейса: **русский и узбекский** (`ru` / `uz`).

Три роли:
| Роль | Кто | Что делает |
|---|---|---|
| `client` | клиент | ищет мастера, записывается, оценивает визит, ведёт избранное |
| `stylist` | мастер | подтверждает заявки, ведёт расписание, услуги, портфолио, смотрит статистику |
| `owner` / админ | владелец сервиса | веб-панель: пользователи, тарифы, барбершопы, справочник услуг |

Монетизация: подписка мастера (`users.subscription_until`). Истёк срок → мастер пропадает
из поиска, его меню сворачивается до «Срок тарифа».

## 3. Команды

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

```bash
alembic upgrade head   # накатить схему (бот делает это сам на старте)
python bot.py          # только бот (polling)
python admin_panel.py  # только админка на 127.0.0.1:8002
python launcher.py     # бот + админка вместе
```

Тесты:

```bash
.venv/Scripts/python.exe -m pytest tests/ -q
```

Проверка синтаксиса всего проекта перед отдачей результата:

```bash
python -m compileall -q bot.py admin_panel.py database.py scheduler.py config.py utils.py texts.py launcher.py
```

Сборка Windows-версии:

```bash
pyinstaller Maestro.spec
```

Вся система в контейнерах (бот, админка, PostgreSQL, Redis):

```bash
docker compose up -d
```

Тесты на той же базе, что в проде, — иначе поддержка PostgreSQL протухает молча:

```bash
TEST_DATABASE_URL=postgresql+asyncpg://postgres:pass@127.0.0.1:5432/postgres pytest tests/ -q
```

## 4. Жёсткие правила (нарушение = баг в проде)

### 4.1 Кодировка — критично
В репозитории **однажды уже сгорело 35 строк интерфейса**: кириллица схлопнулась
в `"?????? ??????."` из-за записи файла в неверной кодировке (`docs/AUDIT.md`, A-1).
Строки восстановлены вручную — текст был утрачен безвозвратно. Не повтори это.

- Все `.py`, `.md`, `.json` — **только UTF-8 без BOM**.
- **Никогда** не пиши файлы с кириллицей через `bash` heredoc / `echo` / `sed` на Windows.
  Используй инструмент `Write` / `Edit`.
- После правки файла с кириллицей — проверь: `grep -n '???' <файл>` должен вернуть пусто.
- Дописывание через `cat >>` / `echo >>` оставляет **смешанные окончания строк** даже тогда,
  когда кириллица уцелела: файл в CRLF, дописанное в LF. `check_encoding.py` это ловит.
  Правило нарушалось и после того, как было записано, — поэтому оно теперь проверяется
  машиной, а не памятью.
- Не создавай новые `\uXXXX`-escape-последовательности в исходниках. Пиши текст как есть.
  Существующие escape'ы — легаси, заменяй на нормальный текст при рефакторинге.
- Если в тесте нужен литерал, похожий на порчу (кириллица вплотную перед `\n`,
  три знака вопроса, суррогатная пара) — собирай его из частей: `"Али" + chr(10) + "Валиев"`.
  `check_encoding.py` разбирает литералы и не отличает нарочную фикстуру от настоящего бага.

### 4.2 База данных
- **Не запускай `seed_db.py`** — внутри `drop_all()`.
- Не вызывай `Base.metadata.drop_all` нигде и никогда.
- Схема меняется **только через Alembic-миграцию**. Источник правды — `migrations/`,
  а не `create_all()`: бот и админка на старте вызывают `db.run_migrations()`.
  Новая миграция: `alembic revision --autogenerate -m "ascii_slug"` (slug только латиницей),
  затем обязательно прочитать и поправить сгенерированный файл.
  У каждой миграции должен работать `downgrade` — это проверяется тестом.
- Время визита — это `Booking.starts_at` / `ends_at` типа `DateTime`, **наивное локальное
  Asia/Tashkent**. Обоснование выбора зоны — в докстринге `timeutils.py`.
- Не используй `datetime.now()` и `date.today()` напрямую: только `timeutils.now()` и
  `timeutils.today()`. Не смешивай наивные datetime с aware — сравнение бросит TypeError.
- В SQLite включена проверка внешних ключей (`PRAGMA foreign_keys=ON`). Без неё ошибка
  в порядке удаления проходила бы локально и падала только на PostgreSQL.
- Удаляешь пользователя — только через `services.privacy`: там порядок шагов
  и правило «обезличить, а не стереть» для того, от чего зависят другие.
- Выборки за период — через `timeutils.day_bounds()` / `range_bounds()`, это полуинтервалы
  `[начало, конец)`. Никаких `LIKE` по дате: они не используют индекс.

### 4.3 Асинхронность и ORM
- Ленивая подгрузка связей в async-контексте **падает** (`MissingGreenlet`). Всегда указывай
  `joinedload()` / `selectinload()` для каждой связи, к которой обращаешься.
  Именно из-за этого часовое напоминание молча не отправлялось несколько месяцев
  (`scheduler.py`, `b.stylist.name` без `joinedload`).
- Одна сессия = одна логическая операция. Не держи `async with db.async_session()` открытым
  вокруг сетевых вызовов Telegram.
- Любая отправка сообщения пользователю оборачивается в `try/except TelegramAPIError`
  (пользователь мог заблокировать бота). Но **не глуши исключения пустым `except: pass`** —
  логируй через `logging.warning` с контекстом.

### 4.4 Безопасность хендлеров
- Каждый callback, меняющий чужие данные, **обязан проверять право вызывающего**.
  Идентификатор из `callback_data` — недоверенный ввод. Готовые помощники:
  `services.access.load_booking_for_stylist()` / `load_booking_for_client()` — сверяют
  владельца прямо в SQL-запросе; `guards.deny_access(cb)` — отказ с ответом пользователю.
  Для действий мастера над своим профилем — `guards.ensure_active_stylist_callback()`.
- Никогда не восстанавливай состояние из текста сообщения (`cb.message.text.split(":")`).
  Источник истины — база.
- Меняешь статус записи — пиши в журнал (`services.audit`) **в той же сессии**,
  до `commit()`. Отдельная транзакция означает, что при сбое изменение есть,
  а следа нет. Проверяется тестами, читающими исходники хендлеров.
- Сравнивать секреты — через `security.constant_time_equals()`, а не
  `secrets.compare_digest` напрямую: на объектах `str` он требует ASCII
  и на кириллическом пароле бросает `TypeError` вместо отказа.
- Новое представление в админке наследуется от `RoleAwareView`. Право на запись
  выдаётся явно через `writable_by`, по умолчанию — только владелец.
- Не логируй `BOT_TOKEN`, номера телефонов и `telegram_id` в открытом виде.
  Для идентификатора есть `logutil.mask_user()`; строка `user_id=%s` рядом с telegram_id
  роняет `test_source_has_no_plain_user_id_logging`.

### 4.5 UX
- Любое действие пользователя должно получать ответ: `cb.answer()` обязателен в конце
  каждого callback-хендлера, иначе в клиенте висит «часики».
- На каждом экране должна быть кнопка «Назад» или «Главное меню». Тупиков быть не должно.
- Новый текст для пользователя добавляется **сразу на двух языках** (`ru` + `uz`) и
  **только через `texts.py`**, не инлайн-словарём в хендлере. Для всего `handlers/`
  это проверяется тестом: русский литерал в коде роняет `test_stylist_panel_i18n`.
- Уведомление другому человеку (мастеру о заявке, клиенту о подтверждении) — на языке
  **получателя**, а не того, кто нажал кнопку.
- Фильтр по тексту кнопки строится через `texts.all_variants(key)`, а не сравнением
  с одной строкой: иначе после переключения языка кнопка молча перестаёт работать.
- Функция, которая собирает текст или клавиатуру, **принимает язык явным аргументом**.
  Перевод, лежащий в `texts.py`, но не получивший язык от вызывающего кода,
  не доезжает до пользователя — и это не видно ни линтеру, ни тестам словарей.
- Подробные правила — `docs/UX_GUIDELINES.md`.

### 4.6 Git
- Логи, `.db`, `dist/`, `build/`, `.env` — не коммитить.
- Ветка `main` защищена по смыслу: новые изменения — через ветку и PR.
- Не делай `git push`, `git commit` и `gh pr create` без явной просьбы пользователя.

## 5. Как я работаю над задачами

1. **Сначала читаю** `docs/ROADMAP.md` — есть ли задача там. Если есть, работаю по ней и
   после завершения ставлю `[x]` в том же коммите.
2. Задачи беру **по фазам, сверху вниз**. Не начинаю Фазу 2, пока не закрыта Фаза 1,
   если пользователь не сказал иначе.
3. Конфликты префиксов `callback_data` проверяет `tests/test_callback_collisions.py`:
   он разбирает исходники, восстанавливает реальный порядок проверки фильтров
   и падает, если один префикс перехватывает нажатия другого. Отдельно закреплены
   три зависимости от порядка: `set_day_off_` раньше `set_day_`,
   `search_district` раньше `search_`, `stylist_card` раньше `booking`.
   Порядок роутеров — в `handlers/__init__.py`, внутри роутера — порядок определения функций.
4. Новый хендлер вешается на `router` своего модуля, а не на `dp`: в aiogram
   диспетчер проверяет собственные хендлеры раньше вложенных роутеров,
   и хендлер на `dp` обойдёт всю расстановку приоритетов.
5. После правок обязательно: `compileall` + `ruff check .` + `python scripts/check_encoding.py`
   + `pytest tests/ -q`. Меняешь бизнес-правило — добавляешь тест в том же коммите.
   `ruff` в списке не для красоты: без него ветка однажды несколько коммитов подряд
   уходила с красным линтером в CI. `pre-commit install` запускает всё это сам.
   `check_encoding.py` ловит и `\uXXXX` вместо текста — инструмент правки однажды
   подхватил этот стиль у файла, где такие escape'ы уже были.
6. Отчитываюсь честно: что сделано, что не проверено, что осталось.

## 6. Целевая архитектура (куда идём)

```
maestro/
├── app/
│   ├── bot/
│   │   ├── handlers/      client/, stylist/, common/
│   │   ├── keyboards/
│   │   ├── middlewares/   auth, i18n, throttling, errors, db-session
│   │   ├── states/
│   │   └── filters/
│   ├── core/              config, logging, exceptions
│   ├── db/                models/, repositories/, migrations/
│   ├── services/          booking, schedule, subscription, rating, notification
│   ├── locales/           ru.ftl / uz.ftl
│   └── admin/             FastAPI + sqladmin
├── tests/
└── docs/
```

Принцип: **хендлер не ходит в базу напрямую**. Хендлер → сервис → репозиторий → ORM.
Бизнес-правила (свободен ли слот, активна ли подписка, можно ли отменить) живут в
`services/` и покрываются тестами.

## 8. Скрипты правки файлов с кириллицей

Массовые правки `bot.py` делаются одноразовым Python-скриптом в scratchpad, а не через
`bash`/`sed` — иначе повторится A-1. Обязательные требования к такому скрипту:

1. Читать и писать только с `encoding="utf-8"`.
2. Проверять ожидаемое число вхождений **до** записи и не трогать файл при несовпадении.
3. Сохранять CRLF: `p.write_bytes(text.replace("

", "
").replace("
", "

").encode("utf-8"))`.
   Без этого diff раздувается на весь файл и изменения невозможно отревьюить.
4. После прогона: `compileall`, `grep -n '???'`, `pytest`.
