## A — блокеры

### A-1. Повреждённая кириллица в интерфейсе
35 строк русского текста превратились в `?????`. Клиент на русском языке видит буквально:

```
?????? ??????. ??????? ??????.          # bot.py:1452 — ошибка сессии при записи
?????? ?? ??????.                       # bot.py:1220 — мастер не найден
? ???? ?????? ???? ??? ???????????.     # bot.py:1046 — нет барбершопов в районе
```

Затронуты **ключевые экраны воронки**: поиск, карточка мастера, выбор услуги, выбор даты,
финализация записи. Русскоязычный клиент на половине пути видит абракадабру.

Причина: файл в какой-то момент сохранили в однобайтовой кодировке, кириллица схлопнулась в `?`.
Восстановить автоматически нельзя — текст утрачен, нужно переписать вручную.

Полный список строк: `grep -n '???' bot.py`.

### A-2. Отсутствие авторизации в callback-хендлерах
```python
@dp.callback_query(F.data.startswith("approve_"))
async def approve_booking(cb: CallbackQuery):
    booking_id = int(cb.data.split("_")[-1])   # ← никакой проверки, чей это booking
```

`approve_`, `decline_`, `complete_`, `rate_` берут `id` прямо из `callback_data` и меняют запись.
Любой пользователь, отправив боту callback `approve_123`, подтверждает **чужую** запись.
Так же `rate_` позволяет накрутить оценку любому мастеру.

Аналогично `del_srv_`, `special_*`, `set_day_*` — проверки «это мой профиль?» нет.

Нужно: middleware/декоратор, который по `cb.from_user.id` достаёт профиль и сверяет
владельца объекта; при несовпадении — `cb.answer("Нет доступа", show_alert=True)`.

### A-3. Рейтинг мастера не считается
`Booking.rating` заполняется в `handle_rating` (`bot.py:2651`), но `Stylist.avg_rating`
**не обновляется нигде в проекте**. Поиск::

```python
grep -rn "avg_rating" *.py   # только чтение, ни одной записи
```

Следствие: в карточке мастера и в топе дашборда рейтинг всегда `0` / «Нет оценок».
Ключевой элемент доверия в маркетплейсе не работает.

Нужно: после сохранения оценки пересчитывать `AVG(rating)` по завершённым записям мастера
и писать в `stylists.avg_rating` (плюс хранить `reviews_count`).

### A-4. Гонка при бронировании слота
`finalize_booking` (`bot.py:1443`): сначала `get_available_slots_for_date`, затем `session.add`.
Между проверкой и вставкой нет блокировки и нет уникального ограничения в БД.
Два клиента, нажавшие один слот одновременно, оба получат «Заявка отправлена».

Нужно: уникальный индекс `(stylist_id, datetime)` для активных статусов + повторная проверка
внутри транзакции + понятная ошибка «слот только что заняли».

### A-5. Напоминание за час не доходит
`scheduler.py:38`: `stylist_name = b.stylist.name`, но в запросе `joinedload` есть только для
`user` и `service`. В async-SQLAlchemy ленивая загрузка бросает `MissingGreenlet`,
исключение ловится общим `except` и пишется в лог. Итог: **ветка часового напоминания
падает каждый раз**, клиент напоминание не получает.

Нужно: добавить `joinedload(db.Booking.stylist)` и перестать глушить исключения целиком.

Там же: окно «за 23–25 часов» проверяется раз в час — при задержке шедулера напоминание
теряется навсегда, потому что флаг не выставлен, а окно прошло.

### A-6. Состояние в оперативной памяти
```python
booking_cache = {}   # bot.py:37
search_cache  = {}
storage = MemoryStorage()
```
Рестарт бота (деплой, падение, перезапуск хостинга) → все незавершённые записи теряются,
клиент получает `?????? ??????` (см. A-1) на последнем шаге.
Также исключает горизонтальное масштабирование.

Нужно: `RedisStorage` для FSM и перенос `booking_cache` в FSM-данные.

### A-7. В репозитории лежат логи и артефакты
`git ls-files` показывает `admin.log`, `nohup.out` (1.2 МБ), `bot.log`, `barberbot.zip`,
`nohup`, `tmp/restart.txt`. Логи содержат операционные данные и раздувают клон.
`.gitignore` их уже игнорирует — но файлы остались в индексе с прошлых коммитов.

Нужно: `git rm --cached`, коммит, при необходимости — чистка истории.

## B — важно

### B-1. Нет миграций
Схема создаётся через `create_all()`. Новая колонка в существующей таблице **не появится**
на боевой базе. Любое развитие модели данных сейчас = ручной SQL на проде.
Нужен Alembic и baseline-миграция под текущую схему.

### B-2. Дата-время как строка
`Booking.datetime: Mapped[str] = mapped_column(String(50))` — комментарий в коде честно
говорит «для простоты». Последствия:
- фильтр «записи на сегодня» = `LIKE 'YYYY-MM-DD%'` → full scan, индекс не применим;
- нет ни одного индекса во всей схеме (`grep index=True database.py` → пусто);
- нет таймзоны, нет валидации, арифметика через `strptime` в каждом месте;
- `get_available_dates_for_month` делает **отдельный запрос на каждый день месяца** —
  до 31 запроса на один показ календаря.

Нужно: `DateTime(timezone=True)`, индексы `(stylist_id, starts_at)`, `(user_id, starts_at)`,
один запрос на месяц вместо 31.

### B-3. Нет экранирования HTML
Сообщения отправляются с `parse_mode="HTML"`, в них подставляются `first_name`, `name`
мастера, названия услуг. Экранирования нет ни одного (`grep -c "escape(" bot.py` → `0`).
Имя вида `<b` ломает отправку сообщения целиком (Telegram вернёт `can't parse entities`),
и хендлер упадёт молча.

Нужно: `html.escape()` для всех пользовательских значений либо переход на `MarkdownV2`
с общей функцией экранирования. Заодно вынести `parse_mode` в `DefaultBotProperties`.

### B-4. Deep-link не обрабатывается
`scheduler.py:88` отправляет `https://t.me/maestro_bot?start={stylist_id}`, но хендлер
`start()` (`bot.py:668`) игнорирует payload. Клиент по ссылке из follow-up попадает
в общее меню вместо карточки мастера — конверсия возвратной кампании теряется.

Нужно: `CommandObject.args` → открыть карточку мастера; заодно использовать payload
для реферальных ссылок мастеров (см. дорожную карту, Фаза 4).

### B-5. Состояние из текста сообщения
`approve_booking` / `decline_booking` восстанавливают карточку заявки, **разбирая текст
уже отправленного сообщения**:
```python
non_empty_lines = [...]
client_name = non_empty_lines[1].split(":", 1)[-1].strip()
```
Любое изменение шаблона ломает логику. Данные есть в `booking` — надо брать из неё.

### B-6. Слабая аутентификация админки
- пароль хранится и сравнивается в открытом виде (`admin_panel.py:28`);
- сравнение не константное по времени;
- нет ограничения попыток входа, нет журнала входов;
- `.env.example` предлагает `admin/admin12345`;
- в дефолте админка слушает `127.0.0.1`, но при деплое это легко меняется — HTTPS и
  обратный прокси не описаны.

Нужно: хеш пароля (`argon2`/`bcrypt`), лимит попыток, аудит-лог действий админа.

### B-7. Нет обработчика ошибок и fallback'а
Нет `@dp.errors` — любое необработанное исключение в хендлере уходит в лог, пользователь
не получает ничего и остаётся перед «зависшим» экраном.
Нет catch-all `@dp.message()` — если пользователь пишет произвольный текст, бот молчит.

### B-8. Нет антифлуда
Ни одного middleware-ограничителя. Быстрое нажатие кнопки «Записаться» порождает
параллельные запросы к БД; повторные нажатия `approve_` создают дублирующие уведомления.

### B-9. Локализация фрагментирована
`texts.py` содержит ~20 ключей, остальные сотни строк — инлайн-словари
`{"ru": ..., "uz": ...}[lang]` прямо в хендлерах. Часть строк вообще только на русском
(`bot.py:1860` «🖼 Мое портфолио», `DAY_LABELS`, всё меню мастера).
Узбекоязычный мастер видит смесь языков. Добавить третий язык сейчас невозможно.

### B-10. Кнопка без обработчика
`get_main_keyboard` для мастера с истёкшим тарифом отдаёт `"🌐 Til"` (`bot.py:652`),
но хендлер языка ловит только значения из `texts.get_buttons`. Кнопка не работает.

## C — технический долг

- **C-1.** `bot.py` — 2687 строк, 90+ хендлеров, бизнес-логика вперемешку с UI.
  Любое изменение рискованно, ревью невозможно.
- **C-2.** Тестов нет. `test_async.py` — 10 строк проверки коннекта. Критичные правила
  (свободен ли слот, активна ли подписка, пересекаются ли брони) не покрыты ничем.
- **C-3.** `F.data.startswith("stylist_")` зарегистрирован дважды (`1097` и `1203`),
  вторая регистрация мертва. Префиксы `search_` / `search_district` тоже пересекаются.
  Плоские строковые префиксы надо заменить на `CallbackData`-фабрики aiogram.
- **C-4.** `print()` и `logging` вперемешку; логи русскоязычные, неструктурированные,
  без correlation-id. Диагностика инцидента на проде почти невозможна.
- **C-5.** Нет `ruff`, `black`, `mypy`, нет CI. `requirements.txt` — плоский pip-freeze
  без разделения на prod/dev.
- **C-6.** Артефакты shared-хостинга: `.htaccess`, `passenger_wsgi.py`, `public/`,
  `.well-known/`, `nohup`, `tmp/restart.txt`, `.codex_pycache/`, два виртуальных окружения
  (`venv/` и `.venv/`), `build/`, `dist/`.
- **C-7.** Только long-polling, `MemoryStorage`, нет graceful shutdown (`engine.dispose()`,
  остановка шедулера), нет `/health` для самого бота, нет метрик.

## Что в проекте сделано хорошо

Чтобы не сломать при рефакторинге:

- модель предметной области адекватная: `Schedule` + `SpecialSchedule` (исключения по датам)
  — правильное разделение, многие такие боты этого не умеют;
- расчёт слотов учитывает длительность услуги и пересечения (`slot_overlaps_existing`);
- подписка мастера сквозной нитью проходит через поиск, карточку и запись — монетизация
  реально работает;
- календарь скрывает дни без свободных слотов — хороший UX-приём;
- есть дашборд с KPI и `/health`;
- есть цепочка удержания: напоминания 24ч/1ч, follow-up на 20-й день, оценка после визита.

Фундамент здоровый. Проблема не в замысле, а в исполнении: нет слоёв, нет тестов,
нет миграций, и текст интерфейса повреждён.
