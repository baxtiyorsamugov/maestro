# Безопасность Maestro

## 1. Что защищаем

| Актив | Риск при компрометации |
|---|---|
| `BOT_TOKEN` | полный контроль над ботом: чтение переписки, рассылка от имени сервиса |
| Персональные данные клиентов (имя, телефон, `telegram_id`, история визитов) | утечка базы клиентов, репутационный и юридический ущерб |
| Учётная запись админки | изменение тарифов, удаление записей, выгрузка всей базы |
| Целостность записей | подтверждение/отмена чужих броней, накрутка рейтинга |

## 2. Текущие уязвимости

### Критично

**S-1. Нет авторизации в callback-хендлерах** — ИСПРАВЛЕНО
`approve_`, `decline_`, `complete_`, `rate_`, `booking_cancel_` брали идентификатор
объекта из `callback_data` и не проверяли, имеет ли отправитель к нему отношение.
Любой пользователь Telegram мог подтвердить чужую запись, накрутить оценку мастеру
или безвозвратно удалить чужую бронь.

Сейчас: `load_booking_for_stylist()` и `load_booking_for_client()` сверяют владельца
прямо в SQL-запросе. Отмена меняет статус, а не удаляет строку. Покрыто тестами.

**S-2. Пароль админки в открытом виде** — ИСПРАВЛЕНО
Хранился в `.env` как есть и сравнивался оператором `==` (не константное время),
без ограничения попыток и журнала входов.

Сейчас: scrypt-хеш (`security.py`, стандартная библиотека — без новых зависимостей),
`secrets.compare_digest` для обоих полей, блокировка на 5 минут после 5 неудачных
попыток с одного адреса, все попытки пишутся в лог. Открытый пароль всё ещё
принимается, чтобы не сломать существующие установки, но при старте выводится
предупреждение. Хеш генерируется скриптом `python scripts/hash_password.py`.

**S-3. Логи в репозитории** — ИСПРАВЛЕНО в индексе, остаются в истории
`admin.log`, `nohup.out` (1.2 МБ), `bot.log` убраны из индекса, в CI стоит проверка
против повторного попадания. **В истории коммитов они остаются** — если решите,
что там есть чувствительные данные, потребуется `git filter-repo` и ротация токена.

**S-9. Пароль админки по умолчанию в истории коммитов** — ТРЕБУЕТ РЕШЕНИЯ ВЛАДЕЛЬЦА
Проверка истории (все 40 коммитов) на секреты дала один результат: в четырёх
коммитах (`8996b45`, `dbe1439`, `895e250`, `65de947`) лежала строка
`ADMIN_PASSWORD = os.getenv("ADMIN_PASSWORD", "barber_secret_pass")`.

Это был не секрет из `.env`, а **значение по умолчанию** в коде. Но если боевая
установка хоть раз запускалась без заданного `ADMIN_PASSWORD`, то паролем админки
был именно он — и он лежит в публичной истории репозитория.

Что проверено и чисто:
- `.env` в индекс никогда не попадал (только `.env.example`);
- боевого `BOT_TOKEN` в истории нет — поиск по шаблону `\d{8,10}:AA[\w-]{30,}`
  по всем коммитам дал только тестовые заглушки;
- паролей БД в истории нет.

Что делать владельцу:
1. Сменить пароль админки, если он когда-либо совпадал с `barber_secret_pass`.
2. Решить, нужна ли перезапись истории (`git filter-repo`). Значение по умолчанию —
   не то же самое, что утёкший боевой секрет, поэтому это не обязательно.

Сейчас в коде дефолта нет: `load_admin_settings()` требует все три переменные
через `get_required_env()` и падает на старте, если их нет.

### Важно

**S-4. Нет экранирования HTML** — ИСПРАВЛЕНО. Пользовательские значения
проходят через `html.escape()`. Раньше имя вида `<b` ломало отправку сообщения целиком.

**S-5. Нет антифлуда.** Отсутствует throttling — бот открыт для перебора callback'ов
и для исчерпания пула соединений к БД.

**S-6. Гонка при бронировании** — ИСПРАВЛЕНО на SQLite и PostgreSQL частичным
уникальным индексом `uq_active_booking_slot`. **MySQL частичные индексы не поддерживает**,
там защитой остаётся только перепроверка в транзакции.

**S-7. `.env` рядом с `.exe`.** Windows-сборка требует положить `.env` с боевым токеном
рядом с исполняемым файлом. Любой, у кого есть копия дистрибутива, получает токен
и доступ к базе. Раздавать `.exe` с боевым `.env` нельзя.

**S-8. Нет модели удаления данных.** Пользователь не может удалить свой аккаунт и историю.

## 3. Правила для разработки

- Секреты — только в `.env`, никогда в коде, коммитах, логах и сообщениях об ошибках.
- `.env.example` содержит **плейсхолдеры**, а не рабочие значения.
- `ADMIN_SECRET_KEY` — не меньше 32 случайных байт, свой для каждого окружения.
- Каждый хендлер, меняющий данные, начинается с проверки прав. Без исключений.
- Идентификаторы из `callback_data` — **недоверенный ввод**. Всегда сверяем с владельцем.
- Пользовательский ввод не попадает в HTML-сообщения без `html.escape()`.
- В логи не пишем токены, пароли и полные номера телефонов.
- Админка не выставляется в интернет без HTTPS и обратного прокси.
- Зависимости обновляются регулярно; в CI — `pip-audit`.

## 4. Чек-лист перед выходом в прод

- [x] `BOT_TOKEN` не встречается ни в одном коммите за всю историю (проверено)
- [x] Логи, `.db`, `.env`, архивы удалены из индекса git (и проверяются в CI)
- [x] Пароль админки захеширован, дефолтные учётные данные заменены
- [x] Ограничение попыток входа в админку включено
- [x] Все callback-хендлеры проверяют права (S-1 закрыт)
- [ ] Throttling-middleware включён
- [x] Уникальное ограничение на слот в БД создано (кроме MySQL)
- [ ] Админка только по HTTPS, доступ ограничен по IP или VPN
- [ ] Бэкапы базы настроены и **восстановление проверено на копии**
- [ ] Sentry подключён, в события не попадают персональные данные
- [ ] Опубликована политика обработки данных, в боте есть `/privacy`
- [ ] Реализовано удаление аккаунта и данных по запросу пользователя

## 5. Если токен утёк

1. @BotFather → `/revoke` → получить новый токен.
2. Обновить `.env` на всех окружениях, перезапустить бота.
3. Проверить логи Telegram на посторонние рассылки.
4. Удалить старый токен из истории git (`git filter-repo`), уведомить всех, у кого есть клоны.
5. Сменить `ADMIN_SECRET_KEY` и пароль админки — сессии станут недействительны.
