# Развёртывание Maestro

## Быстрый старт

```bash
cp .env.example .env
# заполните .env: BOT_TOKEN, DB_PASS, ADMIN_*
docker compose up -d
```

Поднимается четыре сервиса: `db` (PostgreSQL 16), `redis`, `bot` (polling),
`admin` (uvicorn на `127.0.0.1:8002`). Миграции бот и админка накатывают сами
на старте — отдельного шага не нужно.

Проверка, что всё живо:

```bash
curl http://127.0.0.1:8002/health
```

Ответ `{"status":"ok", ..., "database":"ok"}` означает, что админка поднялась
и достучалась до базы.

---

## Почему PostgreSQL

Не ради моды. Частичный уникальный индекс `uq_active_booking_slot` —
единственная настоящая защита от двойной брони — создаётся только на
PostgreSQL и SQLite. **MySQL частичные индексы не поддерживает**, и там
защитой остаётся одна перепроверка слота в транзакции, которая гонку
закрывает не полностью (`docs/SECURITY.md`, S-6).

SQLite остаётся для локальной разработки и Windows-сборки: `DB_DRIVER=sqlite`.

Переменные для сервера:

```
DB_DRIVER=postgres     # или mysql, если PostgreSQL недоступен
DB_HOST=db
DB_PORT=5432
DB_USER=maestro
DB_PASS=...
DB_NAME=maestro
```

Либо одной строкой через `DATABASE_URL` — она имеет приоритет над всем выше.

## Что обязательно задать

Окружение проверяется на старте, и бот не поднимется, пока оно не заполнено.
Все претензии печатаются одним списком, а не по одной за запуск:

```
Окружение настроено не полностью:
  BOT_TOKEN: не задана
  ADMIN_SECRET_KEY: короче 32 символов — сгенерируйте новый: ...
```

| Переменная | Зачем |
|---|---|
| `BOT_TOKEN` | токен у @BotFather; проверяется на формат, а не только на наличие |
| `DB_PASS` | пароль PostgreSQL; `docker compose` без него не стартует |
| `ADMIN_USERNAME` / `ADMIN_PASSWORD` | вход в веб-панель |
| `ADMIN_SECRET_KEY` | подпись сессий, не короче 32 символов |
| `REDIS_URL` | в compose задаётся автоматически; без него FSM теряется при рестарте |
| `LOG_SALT` | соль для маскировки `telegram_id` в логах; необязательна, но желательна |
| `ADMIN_MANAGER_USERNAME` / `ADMIN_MANAGER_PASSWORD` | вторая учётная запись: смотреть всё, менять только записи. Необязательна |

Пароль админки хранится хешем: `python scripts/hash_password.py` выдаёт строку,
которую целиком кладут в `ADMIN_PASSWORD`. Открытый пароль тоже принимается —
с предупреждением в логе, чтобы не ломать существующие установки.

## Админка наружу

В `docker-compose.yml` порт админки проброшен **только на localhost хоста**:

```yaml
ports:
  - "127.0.0.1:8002:8002"
```

Это намеренно. Наружу её выставляют через nginx с HTTPS, а не портом
контейнера: у панели нет ни собственного TLS, ни защиты от перебора
на сетевом уровне (лимит попыток входа есть в самом приложении).

База наружу не публикуется вовсе.

## Вебхук

Без `WEBHOOK_URL` бот работает поллингом — так удобно локально. На проде
нужен вебхук:

- **рестарт без потерь.** При поллинге бот на старте сбрасывал накопившиеся
  апдейты, то есть нажатия людей во время деплоя пропадали. Вебхук ставится
  с `drop_pending_updates=False`: Telegram держит недоставленное у себя
  и отдаёт после подъёма;
- **нет постоянного соединения** к Telegram из процесса и конфликта
  «два процесса поллят один токен».

В `.env`:

```bash
WEBHOOK_URL=https://bot.example.uz
WEBHOOK_SECRET=...   # python -c "import secrets; print(secrets.token_urlsafe(48))"
```

Бот на старте сам вызывает `setWebhook` с этим секретом. Запрос без заголовка
`X-Telegram-Bot-Api-Secret-Token` или с чужим значением получает 401 и до
хендлеров не доходит. Без секрета вебхук не запускается вовсе — `check_environment`
откажет на старте: иначе любой, кто узнал адрес, слал бы поддельные нажатия
от имени любого пользователя, включая «подтвердить запись».

Контейнер слушает `127.0.0.1:8081` хоста. Наружу — через nginx:

```nginx
server {
    listen 443 ssl http2;
    server_name bot.example.uz;

    ssl_certificate     /etc/letsencrypt/live/bot.example.uz/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/bot.example.uz/privkey.pem;

    # Только путь вебхука. /health наружу не нужен — его смотрят локально.
    location = /telegram/webhook {
        proxy_pass http://127.0.0.1:8081;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        client_max_body_size 1m;
    }

    location / {
        return 404;
    }
}
```

Проверка после деплоя:

```bash
curl -s http://127.0.0.1:8081/health
curl -s "https://api.telegram.org/bot$BOT_TOKEN/getWebhookInfo"
```

Во втором ответе `url` должен совпадать с вашим адресом, `pending_update_count`
— уменьшаться до нуля, а `last_error_message` — отсутствовать.

**Вернуться на поллинг:** убрать `WEBHOOK_URL` и перезапустить бота. На старте
поллинга вебхук снимается автоматически — пока он стоит, `getUpdates` не работает.

## Бэкапы

### Снять копию

```bash
python scripts/backup_db.py --docker-service db --keep 14
```

`--docker-service db` запускает `pg_dump` **внутри контейнера базы**. Это не
удобство: при развёртывании через compose клиента PostgreSQL на хосте обычно
нет вовсе, а в образе базы он есть — и, что важнее, той же версии, что и
сервер. `pg_dump` старше сервера просто отказывается работать, и узнать об
этом в момент аварии — плохой план.

Без Docker (обычный сервер с `postgresql-client`) флаг не нужен:

```bash
python scripts/backup_db.py --out /var/backups/maestro --keep 30
```

Формат — обычный SQL под gzip, а не кастомный формат `pg_dump`. Восстановление
из кастомного формата требует `pg_restore` подходящей версии и разбирательства
с флагами; обычный SQL разворачивается одной командой, которую можно набрать
руками в три часа ночи, и его содержимое видно глазами.

Скрипт возвращает ненулевой код при любой неудаче и удаляет пустой файл, если
дамп не получился: тихо упавший бэкап обнаруживается в тот день, когда он нужен.

### По расписанию

```cron
0 3 * * * cd /opt/maestro && /usr/bin/python3 scripts/backup_db.py --docker-service db --keep 14 >> /var/log/maestro-backup.log 2>&1
```

Раз в неделю имеет смысл прогонять проверку восстановления — см. ниже.

### Восстановление

```bash
gunzip -c backups/maestro-20260920-030000.sql.gz \
  | docker compose exec -T db psql -U maestro -d maestro --set ON_ERROR_STOP=1
```

`ON_ERROR_STOP=1` обязателен: дамп, развернувшийся наполовину, хуже
не развернувшегося — он выглядит рабочим.

### Проверка, что бэкап восстанавливается

Бэкап, из которого никто не пробовал восстановиться, бэкапом не является:
он превращается в файл, про который все уверены, что он поможет.

```bash
python scripts/verify_backup.py --docker-service db backups/maestro-20260920-030000.sql.gz
```

Скрипт разворачивает дамп во **временную** базу рядом с боевой, сверяет число
строк в ключевых таблицах и удаляет временную базу за собой. Боевая база
при этом не трогается вовсе.

```
таблица          в базе  из бэкапа
audit_log             3          3
bookings              3          3
services              1          1
stylists              1          1
users                 1          1

Восстановление прошло, данные сошлись.
```

Код возврата: `0` — сошлось, `2` — числа разошлись (нормально, если после
снятия дампа в базу успели записать; посмотрите на время файла), `1` — дамп
не развернулся вовсе.

### Что проверено вживую

Полный цикл прогнан на этой конфигурации, а не выведен теоретически:

1. База наполнена через сам проект (мастер, клиент, три записи, журнал);
2. снят дамп командой выше — внутри него оказались схема, частичный индекс
   `uq_active_booking_slot` и кириллица;
3. схема снесена целиком (`DROP SCHEMA public CASCADE`) — осталось 0 таблиц;
4. восстановление прошло той самой командой из этого раздела;
5. вернулись все строки, кириллица не пострадала, и **защита от двойной
   брони восстановилась вместе со схемой**.

Последний пункт стоит проверять и впредь: дамп без этого индекса выглядит
полноценным, но оставляет сервис без единственной настоящей защиты от
двойной брони.

## Ошибки: Sentry

Без `SENTRY_DSN` ничего не включается — локальная разработка и тесты идут
без Sentry вовсе. С DSN обе половины шлют в один проект, различаясь тегом
`component` (`bot` / `admin`).

```
SENTRY_DSN=https://...@...ingest.sentry.io/...
SENTRY_ENVIRONMENT=production
```

Подключение — меньшая часть работы. Большая — **вычистить из событий то, чему
в них не место**. Sentry по умолчанию щедро прикладывает контекст: тело
запроса, локальные переменные кадров стека, заголовки. В этом проекте в таком
контексте живут номера телефонов, `telegram_id`, пароль админки и `BOT_TOKEN`.

`observability.before_send` вырезает:

- поля по имени — `password`, `secret_key`, `phone_number`, `db_pass` и прочие;
- токен бота **по форме**, где бы он ни лежал в тексте. Это важнее, чем кажется:
  в сообщении от aiohttp токен приходит внутри URL, вплотную за `bot`, и поиска
  по имени поля там нет вовсе;
- телефоны узбекского формата по форме;
- `telegram_id` заменяется маскированным токеном: ошибки одного человека
  по-прежнему связываются между собой, но кто это — из события не узнать.

Плюс `send_default_pii=False` и `include_local_variables=False`: не отправлять
данные надёжнее, чем вычищать их.

Проверено на настоящем событии, собранном самим `sentry-sdk` из реального
исключения: токен, телефон, пароль, `telegram_id`, IP и имя пользователя
не уехали, а тип исключения, теги и идентификатор записи остались.

## Роли в панели

Учётных записи две, обе задаются окружением:

| Роль | Что может |
|---|---|
| `owner` (`ADMIN_USERNAME`) | всё: тарифы, учётные записи, справочники, модерация отзывов |
| `manager` (`ADMIN_MANAGER_USERNAME`) | смотреть всё, менять только записи |

Помощник нужен, чтобы администратор на ресепшене разбирал заявки, не имея
доступа к тарифам мастеров и учётным записям клиентов.

Право на запись выдаётся **явно** (`RoleAwareView.writable_by`), а не
отбирается: новое представление по умолчанию достаётся владельцу. Сессия
без роли считается недействительной — после обновления все входят заново.

Кнопки, которых у помощника нет прав нажимать, ему не показываются: кнопка,
отвечающая отказом, хуже отсутствующей — человек решит, что панель сломана,
а не что у него нет прав. Но проверка стоит и на сервере: прямой POST
в обход интерфейса тоже отклоняется.

**Ограничение:** учётные записи в окружении, а не в таблице. Третий человек
требует правки `.env` и перезапуска. Для сервиса с владельцем и одним
помощником это соразмерно; таблица потребовала бы миграции, UI управления
пользователями и восстановления пароля.

## Логи и метрики

### Логи

В контейнере лог выводится в JSON — одна строка, один объект:

```json
{"ts": "2026-09-20T23:29:39.364+05:00", "level": "INFO", "logger": "uvicorn.error", "message": "Application startup complete."}
```

Формат задаётся `LOG_FORMAT` (`json` в compose, `text` по умолчанию: JSON
в терминале при локальной разработке читать невозможно). Уровень — `LOG_LEVEL`.

Две тонкости, из-за которых JSON раньше молча не работал бы:

- **Alembic** вызывал `fileConfig` и заменял обработчики корневого логгера
  целиком. Бот и админка накатывают миграции на старте, так что формат
  сбрасывался к алембиковскому при каждом запуске — то есть всегда.
  Теперь `fileConfig` применяется, только когда Alembic запущен сам по себе.
- **Uvicorn** ставит собственные обработчики на свои логгеры и отключает
  `propagate`: четыре строки о старте уходили мимо формата. `setup_logging`
  снимает их и возвращает распространение к корню.

Время — со смещением (`+05:00`), в отличие от базы, где оно намеренно наивное.
Лог читает не только человек: сборщик примет время без смещения за UTC
и сдвинет всю картину на пять часов ровно тогда, когда по ней разбирают
инцидент. При этом показания часов совпадают со временем записей в базе.

Ротация нужна только при записи в файл (`LOG_FILE`): в контейнере лог уходит
в stdout, и его вращает сам Docker.

### Метрики

```bash
curl http://127.0.0.1:8002/metrics
```

Текстовый формат Prometheus — не потому, что Prometheus обязательно будет,
а потому, что этот формат читают все системы наблюдения и, при нужде, глаза.

```
maestro_bookings_pending_stale 1
```

Эндпоинт без авторизации намеренно: система наблюдения ходит сюда без сессии,
а внутри только агрегаты — ни одного персонального значения. Наружу он всё
равно не торчит, порт админки проброшен на localhost.

### Алерты

`/health` отвечает «жив или нет», и этого мало: сервис бывает живым и при этом
сломанным. Заявка, которую мастер не разобрал третьи сутки, ничего не роняет —
клиент просто не дождался ответа и ушёл.

Раз в день в 9:00 бот присылает сводку владельцу:

```
Maestro: требует внимания

• Заявок без ответа мастера дольше 24 ч.: 1. Клиент столько не ждёт.
• На сегодня нет ни одной записи.
```

Адресат задаётся `ALERT_CHAT_ID` (свой чат или канал администраторов).
Без него задача не делает ничего.

**Когда сказать нечего — сообщения не будет.** Ежедневное «всё хорошо»
читать перестают через неделю, и вместе с ним перестают читать настоящие
предупреждения.

Застарелость считается по времени подачи заявки, а не по дате визита: запись
на следующий месяц, поданная час назад, застарелой не является. Метрика,
считающая иначе, будила бы владельца зря — а разбуженный зря трижды
перестаёт читать алерты вообще.

## Обновление

```bash
git pull
docker compose build
docker compose up -d
```

Новые миграции накатятся при старте. Перед обновлением с миграциями,
меняющими схему, снимите дамп:

```bash
docker compose exec db pg_dump -U maestro maestro > backup-$(date +%F).sql
```

Отдельно про откат: `downgrade` у миграции `f2b840c65e19` **удаляет записи
офлайн-клиентов** — в старой схеме они непредставимы. Это описано в самой
миграции, но перед откатом на проде дамп обязателен.

## Тесты на той же базе, что в проде

Набор тестов по умолчанию идёт на временной SQLite — быстро и без внешних
зависимостей. Но поддержка PostgreSQL, которую никто не прогоняет, протухает
молча: одна миграция уже не накатывалась на PostgreSQL вовсе, потому что
передавала время строкой, а `asyncpg` строку в `timestamp` не принимает.

Поэтому тот же набор умеет идти на PostgreSQL:

```bash
docker run -d --name pg -e POSTGRES_PASSWORD=pass -p 5432:5432 postgres:16-alpine
TEST_DATABASE_URL=postgresql+asyncpg://postgres:pass@127.0.0.1:5432/postgres pytest tests/ -q
```

В CI это отдельная задача `Тесты на PostgreSQL`, она идёт при каждом пуше.
